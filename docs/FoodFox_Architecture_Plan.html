1. Обзор продукта

FoodFox — цифровая платформа сопровождения пациентов после теста FOX Food Xplorer (286 пищевых антигенов, IgG-анализ). Клиент загружает PDF-отчёт, система распознаёт результаты, классифицирует продукты по зонам и формирует персональный план питания. Для «зелёных» (разрешённых) продуктов приложение показывает специальные рецепты из админки.

Ключевой инсайт (CustDev): пользователи ищут не просто результаты теста, а руководство и сопровождение. Приложение — инструмент нутрициолога, а не замена специалиста. Доверие к тесту возникает через специалиста.

Что делает система

  1. Клиент загружает PDF-отчёт FOX
  2. Система распознаёт 286 антигенов и уровни IgG (мкг/мл)
  3. Классифицирует продукты: 🟢 зелёная / 🟡 жёлтая / 🔴 красная зона
  4. Генерирует 4-шаговый протокол ведения (4–6 месяцев)
  5. Показывает рецепты только из разрешённых ингредиентов
  6. Нутрициолог проверяет и корректирует план

3. Архитектура системы

Три слоя

СлойКомпоненты
ДанныеFOX PDF (286 антигенов), Knowledge Base (35 файлов), Рецепты из админки
ИнтеллектПарсер отчёта, Rule Engine протокола, Ротационный планировщик, Молочный профиль Bos d 4/5/8
ИнтерфейсыFlutter (клиент), Web (нутрициолог), Web (админка)

Схема компонентов

  • Flutter App → API Gateway (REST) → Auth, Report, Plan, Recipe Services
  • Report Service → Queue (Redis) → PDF Parser Worker (Python)
  • PostgreSQL — основные данные; S3/Supabase Storage — PDF и фото; Redis — очереди и кэш
  • Web Admin + Web Nutritionist → тот же API

4. Доменная модель данных

Справочники

  • food_items — 286 антигенов FOX (13 категорий)
  • food_categories — овощи, мясо, рыба, зерновые, орехи, бобовые, фрукты, специи, грибы, новые продукты, кофе/чай, прочие
  • food_families — биологические семейства для ротации (dairy, gluten_wheat, nightshades…)
  • food_aliases — синонимы («Солея» = «Морской язык»)
  • special_rules — Bos d 4/5/8, глютеновые фракции

Клиентский путь

  • users, client_profiles — симптомы, анамнез, привязка к нутрициологу
  • reports — PDF, статус парсинга, metadata (QR, patient_id, дата)
  • test_results — food_item_id, value_ug_ml, zone, confidence
  • nutrition_plans — активный план, текущая фаза, даты
  • plan_phases — elimination / reintroduction / yellow / retest
  • rotation_schedule — календарь жёлтых продуктов
  • reintroduction_log — продукт, дата, симптомы 48–72ч
  • symptom_diary — ежедневные записи

Контент

  • kb_articles — статьи из Knowledge Base
  • recipes + recipe_ingredients — рецепты с привязкой к food_items
  • interpretation_blocks — тексты интерпретации

5. Пайплайн распознавания FOX-отчёта

Этапы

  1. Клиент загружает PDF → сохранение в Object Storage
  2. Задача в очередь → Parser Worker
  3. Извлечение текста (pdfplumber / PyMuPDF)
  4. Regex-парсинг: «{название} {число} мкг/мл» или «≤ 5,00 мкг/мл»
  5. Fuzzy match названий к справочнику (rapidfuzz + aliases)
  6. LLM-валидация (опционально) — сверка 286 позиций
  7. Human review если confidence < 85%
  8. Генерация плана → статус awaiting_nutritionist_review
Обязательно: план не активируется без подтверждения нутрициологом (или явного opt-in «работаю самостоятельно» с усиленным disclaimer).

6. Plan Engine — протокол ведения

4-шаговый протокол (4–6 месяцев)

ШагФазаСрокДействия
1Элиминация4–6 недельИсключить 🔴 полностью; 🟡 — ротация (1 раз в 4 дня); цель — восстановление слизистой
2Реинтродукцияс 5–6 неделиВводить 🔴 по одному, интервал 3 дня, наблюдение 48–72 часа
3Жёлтая зонапри необходимостиЕсли симптомы остаются — усилить работу с 🟡
4Повторный тест~6 месяцевНовый FOX, сравнение профилей, коррекция рациона

Молочный профиль (специальные правила)

АнтигенТермостабильностьПравило при высоком IgG
Bos d 4 (α-лактальбумин)ТермолабильныйИсключить сырое молоко; выпечка/варёное — допустимо
Bos d 5 (β-лактоглобulin)ТермолабильныйАналогично Bos d 4
Bos d 8 (казеин)ТермостабильныйИсключить ВСЕ молочные, включая печёные

Ротационная диета

Продукты одного биологического семейства чередуются — не употребляются подряд. Пример: пшеница → гречка → рис → овёс с интервалом 4 дня между каждой.

7. Рецепты для зелёных продуктов

Логика подбора

Рецепт показывается клиенту, если все ингредиенты находятся в 🟢 зоне его отчёта. Сортировка по количеству «зелёных» ингредиентов (максимальное использование разрешённого рациона).

Админка рецептов

  • Ингредиенты привязаны к food_items (не свободный текст)
  • Фото, пошаговые инструкции, время, порции, теги
  • Превью: «подходит клиенту X?» — симуляция
  • Bulk import CSV для первичного наполнения

10. Compliance и безопасность

  • Дисклеймер: «IgG ≠ диагноз, интерпретация со специалистом»
  • Не показывать «продукт вреден навсегда» — красная зона временная
  • Не позиционировать как тест на аллергию (IgE)
  • 152-ФЗ: согласие на обработку медданных
  • Шифрование at rest, HTTPS, RBAC, аудит изменений плана
Правильная рамка (из KB): FOX — лабораторный инструмент поддержки персонализированных диетических вмешательств у симптомных пациентов. Не тест на аллергию. Не замена базовой диагностики.

13. Стратегия тестирования мобильного MVP

Важно: Render не хостит нативные мобильные приложения (APK/IPA). Render подходит для backend API и Flutter Web (статический сайт). Для реального мобильного тестирования нужны другие инструменты.

Рекомендуемая схема (гибрид)

ЧтоГдеДля когоСкорость обновления
Backend APIRender Web ServiceВсе клиентыAuto-deploy из Git
Flutter Web (preview)Render Static SiteЗаказчик, дизайнер, быстрые демо~3–5 мин после push
Debug APKGitHub Actions → ArtifactРазработчики, QA~10–15 мин после push
Firebase App DistributionFirebaseКоманда, нутрициологи, beta-тестеры (Android)Авто после CI
TestFlightAppleiOS beta-тестеры~30–60 мин review
Локальноflutter runРазработчик с эмулятором/устройствомМгновенно (hot reload)

Что выбрать на старте MVP

1. Render — для backend (обязательно)

  • FastAPI на Render Web Service (0.0.0.0:$PORT)
  • Parser Worker на Render Background Worker
  • PostgreSQL на Render Postgres
  • PDF/фото — Supabase Storage или S3 (не локальный диск Render!)

2. Flutter Web на Render — для быстрых демо (рекомендуется параллельно)

  • flutter build web → deploy как Static Site на Render
  • URL вида https://foodfox-preview.onrender.com — открывается в браузере за минуты
  • Ограничения: камера/PDF picker работают иначе, UX не 100% как на телефоне, нет push
  • Идеально для: показать заказчику экраны, проверить API-интеграцию, UI-review

3. APK через CI — для реального мобильного тестирования (основной путь)

  • GitHub Actions: на каждый push в main → flutter build apk --debug
  • Артефакт скачивается из GitHub Actions (1 клик)
  • Или автозагрузка в Firebase App Distribution → тестеры получают ссылку на телефон
  • Установка: скачать APK → «Разрешить из неизвестных источников» → установить

4. НЕ делать на старте

  • Публикация в Google Play / App Store — долго, нужны аккаунты, review
  • Сборка release APK вручную каждый раз — медленно
  • Ожидать, что Render «запустит приложение» как web-сервис — это не тот use case

Рекомендуемый pipeline для команды

  1. Разработчик: flutter run на эмуляторе (hot reload, мгновенная итерация)
  2. Push в Git → GitHub Actions собирает debug APK + deploy Flutter Web на Render
  3. Заказчик/нутрициолог: открывает Web preview в браузере ИЛИ ставит APK через Firebase link
  4. Backend API всегда на Render — мобильное приложение и Web смотрят на один URL
Итог: Render — для API и Web-preview. APK — через CI + Firebase App Distribution для настоящего мобильного тестирования. Оба канала параллельно с первой недели разработки.
