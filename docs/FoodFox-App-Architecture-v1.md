# FoodFox — архитектура приложения нутрициологов v1.0

Документ отвечает на ТЗ «FoodFox — Архитектура и план разработки v1.0» и фиксирует решения по стеку, доменной модели и слоям. Дизайн: Figma → страница **«Fox приложение»** (file `BgW10eEDt4u0udy0qlKuy0`).

---

## 1. Продукт в одном абзаце

Клиент сдаёт IgG-тест **FOX Food Xplorer** (≈286 антигенов) → загружает PDF в приложение → система распознаёт значения, раскладывает продукты по зонам 🟢🟡🔴 → **Plan Engine** строит 4-шаговый протокол на 4–6 месяцев → для «зелёных» продуктов показываются **рецепты из админки** → нутрициолог подтверждает и корректирует план.

**Ключевой принцип из CustDev:** приложение — инструмент нутрициолога, а не его замена. План **не активируется** без подтверждения специалиста (или явного opt-in «веду сам» с усиленным дисклеймером).

## 2. Роли и интерфейсы

| Роль | Интерфейс | Платформа |
|------|-----------|-----------|
| Клиент | Мобильное приложение | **Flutter** (iOS + Android) |
| Нутрициолог / врач | Панель ведения | **Web** (Next.js) |
| Контент-менеджер | Админка (рецепты, KB) | **Web** (Next.js) |
| Партнёр FOX | Кабинет + курс | **Web** |

Flutter — **только клиент**. Специалисты работают с ноутбука: таблицы на 286 строк, rich-text, модерация парсинга — это десктопные сценарии.

## 3. Архитектура: три слоя

```
┌──────────────── ИНТЕРФЕЙСЫ ─────────────────┐
│ Flutter (клиент)   Web-нутрициолог   Админка │
└───────────────────────┬─────────────────────┘
                        │ REST / JSON
┌───────────────────────▼─────────────────────┐
│                 API Gateway                  │
│  Auth · Report · Plan · Recipe · Content     │
└───────┬───────────────────────┬─────────────┘
        │ очередь               │
┌───────▼────────┐      ┌───────▼─────────────┐
│ PDF Parser     │      │ PostgreSQL          │
│ Worker         │      │ Object Storage (S3) │
└────────────────┘      └─────────────────────┘
```

### Слой данных
FOX PDF (286 антигенов) · Knowledge Base (35 файлов) · рецепты из админки · справочник продуктов и биологических семейств.

### Слой интеллекта
Парсер отчёта · Rule Engine протокола · ротационный планировщик · молочный профиль Bos d 4/5/8.

### Слой интерфейсов
Flutter-клиент · Web-панель нутрициолога · Web-админка контента.

## 4. Стек: рекомендация

ТЗ предлагает FastAPI + Celery + Supabase + Render. Уточнение по итогам прототипа:

| Компонент | Решение | Комментарий |
|-----------|---------|-------------|
| Mobile | **Flutter** (Riverpod/Bloc) | Один код iOS+Android, офлайн-кэш плана и результатов |
| Web (нутрициолог + админка) | **Next.js** | Уже работает прототип, формы и таблицы |
| API | **Node/Next API** сейчас → выделить сервис при росте | Прототип на Next уже отдаёт auth/report/plan/recipe |
| Парсер PDF | **Отдельный worker** | Сейчас TS-парсер даёт 285/285 на эталонном отчёте; на Python переходить только если появятся ML-задачи |
| Очередь | Redis | Асинхронный парсинг + уведомления |
| БД | **PostgreSQL 16** | JSONB для сырого парсинга, RLS для изоляции клиентов |
| Файлы | **S3-совместимое хранилище** | PDF и фото рецептов. Локальная ФС Render/VPS — ephemeral |
| Auth | Собственная (JWT + refresh) | Уже реализовано, роли `client/nutritionist/admin` |
| Push | FCM | Фазы плана, ретест, сообщения нутрициолога |

> **Важно:** у нас уже есть рабочий парсер FOX-PDF на TypeScript с golden-тестами (285/285 совпадений со справочником на эталонном отчёте). Переписывать его на Python ради соответствия ТЗ смысла нет — это самый рискованный блок, и он уже закрыт.

## 5. Доменная модель

### Справочники
- `food_items` — 286 антигенов FOX (13 категорий)
- `food_categories` — овощи, мясо, рыба, зерновые, орехи, бобовые, фрукты, специи, грибы, новые продукты, кофе/чай, прочие
- `food_families` — биологические семейства для ротации (dairy, gluten_wheat, nightshades…)
- `food_aliases` — синонимы («Солея» = «Морской язык»)
- `special_rules` — Bos d 4/5/8, глютеновые фракции

### Клиентский путь
- `users`, `client_profiles` — симптомы, анамнез, привязка к нутрициологу
- `reports` — PDF, статус парсинга, metadata (QR, patient_id, дата), `parse_confidence`
- `test_results` — `food_item_id`, `value_ug_ml`, `zone`, `confidence`
- `nutrition_plans` → `plan_phases` (elimination / reintroduction / yellow / retest)
- `rotation_schedule` — календарь жёлтой зоны
- `reintroduction_log` — продукт, дата, симптомы 48–72 ч
- `symptom_diary` — ежедневные записи

### Контент
- `recipes` + `recipe_ingredients` — ингредиенты привязаны к `food_items`, **не свободный текст**
- `kb_articles` — статьи Knowledge Base
- `interpretation_blocks` — тексты интерпретации

### Изоляция
`client_id` на всех персональных сущностях. API берёт `clientId` **только из сессии**, плюс Postgres RLS — защита в два слоя.

## 6. Пайплайн распознавания FOX-отчёта

1. Клиент загружает PDF → Object Storage
2. Задача в очередь → Parser Worker
3. Извлечение текста
4. Парсинг строк вида `{название} {число} мкг/мл` и `≤ 5,00 мкг/мл`
5. Fuzzy-match названий к справочнику (+ aliases)
6. Human review, если `confidence < 85%`
7. Генерация плана → статус `awaiting_nutritionist_review`

**Уже покрыто парсером:** двухколоночная вёрстка, табличные блоки, молекулярные подстроки Bos d 4/5/8, CCD + контроль лактоферрина, склейка названий через запятую, многострочные названия, фильтрация служебных и индексных страниц.

**Метрика качества:** `confidence` + покрытие относительно заголовка «ПРОВЕРЕННЫЕ АНТИГЕНЫ: N» возвращаются в ответе API загрузки.

## 7. Plan Engine — протокол 4 шага

| Шаг | Фаза | Срок | Действия |
|-----|------|------|----------|
| 1 | Элиминация | 4–6 недель | 🔴 исключить полностью; 🟡 — ротация 1 раз в 4 дня |
| 2 | Реинтродукция | с 5–6 недели | Вводить 🔴 по одному, интервал 3 дня, наблюдение 48–72 ч |
| 3 | Жёлтая зона | при необходимости | Усиленная работа с 🟡, если симптомы остаются |
| 4 | Повторный тест | ~6 месяцев | Новый FOX, сравнение профилей |

### Молочный профиль (специальные правила)

| Антиген | Термостабильность | Правило при высоком IgG |
|---------|-------------------|--------------------------|
| Bos d 4 (α-лактальбумин) | термолабильный | Исключить сырое молоко; выпечка/варёное — допустимо |
| Bos d 5 (β-лактоглобулин) | термолабильный | Аналогично Bos d 4 |
| Bos d 8 (казеин) | **термостабильный** | Исключить **ВСЕ** молочные, включая печёные |

### Ротационная диета
Продукты одного биологического семейства не идут подряд: пшеница → гречка → рис → овёс с интервалом 4 дня.

## 8. Рецепты для зелёных продуктов

**Логика подбора:** рецепт показывается, если **все** ингредиенты в 🟢 зоне клиента. Сортировка — по количеству зелёных ингредиентов.

**Админка:**
- ингредиенты привязаны к `food_items`
- фото, пошаговые инструкции, время, порции, теги
- превью «подходит клиенту X?» — симуляция на конкретном отчёте
- bulk import CSV для первичного наполнения

## 11. Compliance и безопасность

- Дисклеймер: «IgG ≠ диагноз, интерпретация со специалистом» — на онбординге и в профиле
- Красная зона подаётся как **временная элиминация**, не «вредно навсегда»
- Не позиционировать как тест на аллергию (IgE)
- 152-ФЗ: явное согласие на обработку медданных при регистрации
- Шифрование at rest, HTTPS, RBAC, аудит изменений плана
- LLM-аудит без текста промптов; в контекст модели — только данные текущего клиента

## 12. Roadmap

**MVP (фаза 1)**
Справочник 286 продуктов + семейства + dairy rules · загрузка PDF + парсер + human review · зоны + фаза «Элиминация» · зелёные продукты + рецепты из админки · Flutter: загрузка, результаты, план, рецепты · Web: подтверждение парсинга нутрициологом · дисклеймеры из KB.

**Фаза 2**
Календарь ротации 🟡 · реинтродукция + дневник симптомов · обучающие модули из KB · push-уведомления.

**Фаза 3**
Партнёрская программа (сертификат курса) · сравнение повторных отчётов · AI-ассистент · интеграция с лабораторией (API вместо PDF).
