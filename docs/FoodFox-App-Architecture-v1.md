# FoodFox — архитектура приложения нутрициологов v1.0

Документ отвечает на ТЗ «FoodFox — Архитектура и план разработки v1.0» и фиксирует решения по стеку, доменной модели и слоям. Дизайн: Figma → страница **«Fox приложение»** (file `BgW10eEDt4u0udy0qlKuy0`).

---

## 1. Продукт в одном абзаце

Клиент сдаёт IgG-тест **FOX Food Xplorer** (≈286 антигенов) → загружает PDF в приложение → система распознаёт значения, раскладывает продукты по зонам 🟢🟡🔴 → **Plan Engine** строит 4-шаговый протокол на 4–6 месяцев → для «зелёных» продуктов показываются **рецепты из админки** → нутрициолог подтверждает и корректирует план.

**Ключевой принцип из CustDev:** приложение — инструмент нутрициолога, а не его замена. План **не активируется** без подтверждения специалиста (или явного opt-in «веду сам» с усиленным дисклеймером).

## 2. Роли и интерфейсы

| Роль | Интерфейс | Платформа |
|------|-----------|-----------|
| Клиент | Мобильное приложение | **Flutter** (iOS + Android) |
| Нутрициолог / врач | Панель ведения | **Web** (Next.js) |
| Контент-менеджер | Админка (рецепты, KB) | **Web** (Next.js) |
| Партнёр FOX | Кабинет + курс | **Web** |

Flutter — **только клиент**. Специалисты работают с ноутбука: таблицы на 286 строк, rich-text, модерация парсинга — это десктопные сценарии.

## 3. Архитектура: три слоя

```
┌──────────────── ИНТЕРФЕЙСЫ ─────────────────┐
│ Flutter (клиент)   Web-нутрициолог   Админка │
└───────────────────────┬─────────────────────┘
                        │ REST / JSON
┌───────────────────────▼─────────────────────┐
│                 API Gateway                  │
│  Auth · Report · Plan · Recipe · Content     │
└───────┬───────────────────────┬─────────────┘
        │ очередь               │
┌───────▼────────┐      ┌───────▼─────────────┐
│ PDF Parser     │      │ PostgreSQL          │
│ Worker         │      │ Object Storage (S3) │
└────────────────┘      └─────────────────────┘
```

### Слой данных
FOX PDF (286 антигенов) · Knowledge Base (35 файлов) · рецепты из админки · справочник продуктов и биологических семейств.

### Слой интеллекта
Парсер отчёта · Rule Engine протокола · ротационный планировщик · молочный профиль Bos d 4/5/8.

### Слой интерфейсов
Flutter-клиент · Web-панель нутрициолога · Web-админка контента.

## 4. Стек: рекомендация

ТЗ предлагает FastAPI + Celery + Supabase + Render. Уточнение по итогам прототипа:

| Компонент | Решение | Комментарий |
|-----------|---------|-------------|
| Mobile | **Flutter** (Riverpod/Bloc) | Один код iOS+Android, офлайн-кэш плана и результатов |
| Web (нутрициолог + админка) | **Next.js** | Уже работает прототип, формы и таблицы |
| API | **Node/Next API** сейчас → выделить сервис при росте | Прототип на Next уже отдаёт auth/report/plan/recipe |
| Парсер PDF | **Отдельный worker** | Сейчас TS-парсер даёт 285/285 на эталонном отчёте; на Python переходить только если появятся ML-задачи |
| Очередь | Redis | Асинхронный парсинг + уведомления |
| БД | **PostgreSQL 16** | JSONB для сырого парсинга, RLS для изоляции клиентов |
| Файлы | **S3-совместимое хранилище** | PDF и фото рецептов. Локальная ФС Render/VPS — ephemeral |
| Auth клиента | Телефон + OTP по СМС, затем пин-код и биометрия | Пароля нет; пин хранится на устройстве |
| Auth специалистов | Email + пароль (JWT + refresh) | Роли `client/nutritionist/partner/admin` |
| Push | FCM | Фазы плана, ретест, сообщения нутрициолога |

> **Важно:** у нас уже есть рабочий парсер FOX-PDF на TypeScript с golden-тестами (285/285 совпадений со справочником на эталонном отчёте). Переписывать его на Python ради соответствия ТЗ смысла нет — это самый рискованный блок, и он уже закрыт.

## 5. Доменная модель

### Справочники
- `food_items` — 286 антигенов FOX (13 категорий)
- `food_categories` — овощи, мясо, рыба, зерновые, орехи, бобовые, фрукты, специи, грибы, новые продукты, кофе/чай, прочие
- `food_families` — биологические семейства для ротации (dairy, gluten_wheat, nightshades…)
- `food_aliases` — синонимы («Солея» = «Морской язык»)
- `special_rules` — Bos d 4/5/8, глютеновые фракции

### Клиентский путь
- `users`, `client_profiles` — симптомы, анамнез, привязка к нутрициологу
- `reports` — PDF, статус парсинга, metadata (QR, patient_id, дата), `parse_confidence`
- `test_results` — `food_item_id`, `value_ug_ml`, `zone`, `confidence`
- `nutrition_plans` → `plan_phases` (elimination / reintroduction / yellow / retest)
- `rotation_schedule` — календарь жёлтой зоны
- `reintroduction_log` — продукт, дата, симптомы 48–72 ч
- `symptom_diary` — ежедневные записи

### Контент
- `recipes` + `recipe_ingredients` — ингредиенты привязаны к `food_items`, **не свободный текст**
- `kb_articles` — статьи Knowledge Base
- `interpretation_blocks` — тексты интерпретации

### Изоляция
`client_id` на всех персональных сущностях. API берёт `clientId` **только из сессии**, плюс Postgres RLS — защита в два слоя.

## 6. Пайплайн распознавания FOX-отчёта

1. Клиент загружает PDF → Object Storage
2. Задача в очередь → Parser Worker
3. Извлечение текста
4. Парсинг строк вида `{название} {число} мкг/мл` и `≤ 5,00 мкг/мл`
5. Fuzzy-match названий к справочнику (+ aliases)
6. Human review, если `confidence < 85%`
7. Генерация плана → статус `awaiting_nutritionist_review`

**Уже покрыто парсером:** двухколоночная вёрстка, табличные блоки, молекулярные подстроки Bos d 4/5/8, CCD + контроль лактоферрина, склейка названий через запятую, многострочные названия, фильтрация служебных и индексных страниц.

**Метрика качества:** `confidence` + покрытие относительно заголовка «ПРОВЕРЕННЫЕ АНТИГЕНЫ: N» возвращаются в ответе API загрузки.

## 7. Plan Engine — протокол 4 шага

| Шаг | Фаза | Срок | Действия |
|-----|------|------|----------|
| 1 | Элиминация | 4–6 недель | 🔴 исключить полностью; 🟡 — ротация 1 раз в 4 дня |
| 2 | Реинтродукция | с 5–6 недели | Вводить 🔴 по одному, интервал 3 дня, наблюдение 48–72 ч |
| 3 | Жёлтая зона | при необходимости | Усиленная работа с 🟡, если симптомы остаются |
| 4 | Повторный тест | ~6 месяцев | Новый FOX, сравнение профилей |

### Молочный профиль (специальные правила)

| Антиген | Термостабильность | Правило при высоком IgG |
|---------|-------------------|--------------------------|
| Bos d 4 (α-лактальбумин) | термолабильный | Исключить сырое молоко; выпечка/варёное — допустимо |
| Bos d 5 (β-лактоглобулин) | термолабильный | Аналогично Bos d 4 |
| Bos d 8 (казеин) | **термостабильный** | Исключить **ВСЕ** молочные, включая печёные |

### Ротационная диета
Продукты одного биологического семейства не идут подряд: пшеница → гречка → рис → овёс с интервалом 4 дня.

## 8. Рецепты для зелёных продуктов

**Логика подбора:** рецепт показывается, если **все** ингредиенты в 🟢 зоне клиента. Сортировка — по количеству зелёных ингредиентов.

**Админка:**
- ингредиенты привязаны к `food_items`
- фото, пошаговые инструкции, время, порции, теги
- превью «подходит клиенту X?» — симуляция на конкретном отчёте
- bulk import CSV для первичного наполнения

### Регистрация и вход клиента

Пароля нет. Вход по номеру телефона, дальше пин-код для быстрого возврата и биометрия там, где она доступна.

| # | Экран | Переход |
|---|-------|---------|
| A1 | Номер телефона + согласие 152-ФЗ | → A2 |
| A2 | Код из СМС (4 цифры, повтор через 0:42) | → A3 |
| A3 | Создание пин-кода (4 цифры) | → A4 |
| A4 | Повтор пин-кода, состояние «коды не совпали» | → 01 |
| A5 | Вход по пин-коду при повторном запуске | fallback → вход по СМС |
| A6 | Face ID (iOS) / отпечаток (Android) | fallback → пин-код |

**Правила:**
- Пин-код хранится **только на устройстве** (Keychain / Keystore) и не уходит на сервер
- Биометрия включается после создания пин-кода и всегда имеет fallback на пин
- Сброс пин-кода — через повторный вход по СМС
- Сессия на сервере — refresh-токен, привязанный к устройству

## 9.1. Чат-помощник (AI)

**Назначение:** отвечать на вопросы клиента по **его** отчёту, зонам и текущей фазе протокола.

**Контекст, который получает модель:** зоны из отчёта, текущая неделя и фаза, разрешённые и запрещённые продукты на этот день, упомянутые в вопросе антигены. Данные других клиентов в контекст не попадают.

**Ограничения:**
- Не ставит диагноз, не отменяет назначения нутрициолога
- Красная зона подаётся как временная элиминация с указанием, когда возможна реинтродукция
- На запрос «покажи данные другого пользователя» — отказ (защита от prompt injection)
- Аудит запросов в `llm_requests`: модель, токены, задержка — **без текста промпта**

**Сценарии:** можно ли продукт · чем заменить · что на завтрак · почему исключили · когда вернуть · объясни фазу.

**Эскалация:** кнопка «Спросить нутрициолога» переводит вопрос специалисту в веб-панель.

## 9.2. Веб · Партнёрская программа для нутрициологов

Партнёр рекомендует тест FOX, вносит номер отчёта клиента в свой кабинет и получает вознаграждение.

| # | Экран | Содержание |
|---|-------|-----------|
| WA1 | Вход в кабинет | Email и пароль, восстановление, ссылка на заявку |
| WA2 | Регистрация партнёра | ФИО, контакты, специализация, номер сертификата курса FOX, согласие |
| WA3 | Заявка на модерации | До 1 рабочего дня, что откроется после одобрения |
| W1 | Дашборд | KPI (начислено, клиенты, на проверке, доступно к выплате), реферальный код, таблица отчётов |
| W2 | Загрузка отчёта клиента | Загрузка PDF, распознанные поля, сверка с базой лаборатории |
| W3 | Отчёт подтверждён | Сумма начисления, дата выплаты, что происходит дальше |
| W4 | Начисления и выплаты | Баланс, запрос вывода, история выплат, акты и CSV |
| W5 | Материалы для рекомендации | Реферальная ссылка и QR, файлы, безопасные формулировки |

**Регистрация партнёра:** заявка (WA2) → ручная модерация до 1 рабочего дня (WA3) → доступ в кабинет (W1). До одобрения реферальный код не выдаётся и загрузка отчётов недоступна.

**Два способа привязки отчёта**

1. **Загрузка отчёта (W2)** — основной путь. Клиент присылает партнёру PDF, партнёр загружает его в кабинет. Система извлекает номер, дату и лабораторию из файла, сверяет с базой лаборатории и проверяет, что отчёт ещё не привязан.
2. **Реферальная ссылка / QR (W5)** — клиент переходит по `foodfox.ru/t/{код}`, записывается на тест, отчёт привязывается автоматически без участия партнёра.

**Флоу начисления**

1. Партнёр загружает PDF отчёта клиента
2. Парсер извлекает номер, дату теста и лабораторию; поля показываются партнёру с отметками распознавания
3. Сверка с базой лаборатории: номер существует, отчёт не привязан к другому партнёру
4. Статус: `на проверке` → `начислено` → `выплачено`
5. Клиенту уходит приглашение в приложение; после первого входа он появляется в списке партнёра

**Статусы отчёта:** `Начислено` · `На проверке` · `Не найден` (номер не подтверждён лабораторией или уже привязан к другому партнёру).

### Выплаты (W4)

| Параметр | Значение |
|----------|----------|
| Ставка | фиксированная за подтверждённый отчёт (в макете 2 400 ₽) |
| График | 5-го числа каждого месяца |
| Минимальная сумма вывода | 3 000 ₽ |
| Требование | статус самозанятого или ИП |
| Документы | акт формируется автоматически, выгрузка CSV |
| Статусы выплаты | `Выплачено` · `В обработке` |

Вознаграждение попадает в баланс **только после подтверждения отчёта лабораторией** — до этого сумма висит в блоке «На проверке» и недоступна к выводу.

### Материалы (W5)

Реферальная ссылка + QR (копирование и скачивание) и шесть готовых материалов: презентация о тесте, памятка «кому подходит», инструкция «как сдать тест», посты для соцсетей, шаблоны сообщений клиенту, логотипы и брендбук.

Отдельный блок **«Безопасные формулировки»** из `06_ограничения_и_безопасные_формулировки.md`:

| Можно говорить | Нельзя говорить |
|----------------|-----------------|
| «Тест показывает IgG-реакцию на 285 продуктов» | «Тест на аллергию» — это IgE, другой анализ |
| «Помогает подобрать рацион при симптомах» | «Продукт вреден вам навсегда» |
| «Инструмент поддержки диетологического вмешательства» | «Диагноз по результатам теста» |
| «Исключение временное, на 4–6 недель» | «Заменяет обследование у врача» |

**Модель данных (дополнение):**

```
partners (user_id, referral_code, certification_status,
          payout_details, tax_status)
partner_reports (partner_id, report_number, client_id?, lab, test_date,
                 status, fee_amount, source, confirmed_at)
partner_payouts (partner_id, period, reports_count, amount,
                 method, status, requested_at, paid_at)
partner_materials (slug, title, file_key, format, size_bytes, published)
```

`source` различает привязку по ссылке и ручной ввод — нужно для аналитики канала.

**Анти-фрод:** один номер отчёта — один партнёр; ручная модерация спорных привязок в админке; вознаграждение фиксируется на момент подтверждения; запрос вывода блокируется без налогового статуса.

## 9.3. Состояния и анимации

Спецификация движения **привязана к каждому макету**: под экраном в Figma идёт подпись из трёх частей — номер и название, переход по флоу, и лаймовый блок `АНИМ.` с таймингами именно для этого экрана. Отдельной доски нет намеренно: разработчику не нужно сопоставлять экран со сводной таблицей.

Базовые правила: единая кривая `ease-out cubic (0.22, 1, 0.36, 1)`, длительности 120 / 200 / 240 / 400 мс.

**Принцип:** никаких анимаций на медицинских данных. Значения IgG и зоны появляются сразу и не меняются при скролле — движение допустимо только в оболочке интерфейса.

## 11. Compliance и безопасность

- Дисклеймер: «IgG ≠ диагноз, интерпретация со специалистом» — на онбординге и в профиле
- Красная зона подаётся как **временная элиминация**, не «вредно навсегда»
- Не позиционировать как тест на аллергию (IgE)
- 152-ФЗ: явное согласие на обработку медданных при регистрации
- Шифрование at rest, HTTPS, RBAC, аудит изменений плана
- LLM-аудит без текста промптов; в контекст модели — только данные текущего клиента
